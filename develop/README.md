# フットサルリーグ システム — 実装一式

基本設計書（フットサルリーグ_システム基本設計書）に基づく実装。
GitHub Pages（フロントエンド）× Google Apps Script（バックエンド）× Google Sheets（DB）構成。

## ディレクトリ構成

```
futsal-league-system/
├── frontend/                  … GitHub Pages にそのままデプロイ
│   ├── index.html
│   ├── css/style.css          … 芝生グリーン / グラスモーフィズム / 3D & アニメーション
│   ├── images/                … 背景写真（PC/SP）・トロフィー写真
│   └── js/
│       ├── api.js             … GAS通信モジュール
│       └── app.js             … 画面描画・状態管理・ルーティング
├── backend/                   … Apps Script エディタに貼り付け（コンテナバインド）
│   ├── main.gs                … doGet/doPost ルーティング、submitScore排他制御
│   ├── spreadsheet.gs         … シートCRUD・ID採番・初期セットアップ関数
│   ├── schedule.gs            … コート予約・対戦表自動生成（試合数均等化＋3連戦回避）・確定・入れ替え
│   ├── ranking.gs             … チーム/個人ランキング集計 + キャッシュ
│   └── auth.gs                … 管理者認証・トークン発行/検証
└── docs/
    └── spreadsheet_setup_guide.md   … 構築手順書（この順に作業すればOK）
```

## クイックスタート

1. `docs/spreadsheet_setup_guide.md` の STEP 1〜6 に沿ってスプレッドシート＋GASをデプロイ。
2. `frontend/js/api.js` の `API_BASE_URL` をデプロイ後のWebアプリURLに書き換え。
3. `frontend/` を GitHub Pages にpush。
4. 管理者ログイン（右上の歯車アイコン、パスワードはスクリプトプロパティ or `ilovefutsal`）→
   ①大会作成 → ②コート予約 → ③チーム登録（各部署のエントリーが決まり次第1件ずつ） →
   ④対戦表自動生成（下書き） → ⑤内容確認・試合順調整の上「確定」 →
   各チーム代表者が出場メンバーを登録、の順で運用開始。

## 設計書からの主な実装判断・拡張ポイント

設計書の記述だけでは仕様が確定しない箇所について、以下の通り判断・拡張して実装した。
保守担当が引き継ぐ際は特にこの一覧を確認してください。

| 項目 | 判断・拡張内容 |
| :--- | :--- |
| **チームエントリー／メンバー登録の役割分担** | 運用ルールに合わせ、**チームのエントリー（作成）は管理者専用**（`createTeam`）、**出場メンバーの登録・編集は参加者（代表者）が実施**（`submitMembers`）する2段構成とした。参加チーム承認フローは廃止し、管理者が登録したチームは即座に対戦表生成の対象（`status: APPROVED`）となる。 |
| **出場メンバーの再編集** | `submitMembers` は呼び出しのたびに当該チームの既存名簿を全削除→再登録する「洗い替え」方式。これにより、一度登録済みのチームも何度でも安全に編集し直せる。5名未満でもエントリー可能（空欄行は無視して送信）。 |
| **単一部署チームの部署名自動設定** | 参加形態が「単一部署」の場合、出場メンバー登録画面では部署名の入力欄自体を非表示にし、送信時にチーム名をそのまま部署名として自動設定する（フロント・バックエンド双方で矯正）。**「合同チーム」の場合は部署名の入力を必須**とし、氏名はあるのに部署名が空欄の行はエラー表示（赤枠）にしてブロックする（フロント・バックエンド双方でバリデーション）。 |
| **API拡張** | 設計書 4.2 のAPI一覧（5種）に加え、上記の運用に必要な `createTeam` / `submitMembers` / `createTournament` / `getArchiveYears` の4APIを追加した。 |
| **大会IDの自動解決** | フロントエンドの初期表示を簡略化するため、`tournament_id` に特別値 `"current"` を許容し、バックエンド側で「開催中(IN_PROGRESS) > 準備中(PLANNING)の最新大会」を自動解決する仕様とした。 |
| **参加者の本人確認方式** | 設計書には代表者用の個別ログイン機構の記載がないため、`submitScore` は `team_id` の一致（自チーム選択）のみで信頼するトラストベース方式とした（設計書 5.1 のロジックをそのまま踏襲）。厳密ななりすまし防止が必要な場合は、代表者ごとの簡易PINやトークン発行の追加を推奨。 |
| **チームランキングの勝点ルール** | 設計書に勝点計算式の明記がないため、一般的なリーグ戦ルール（勝=3 / 分=1 / 負=0、同点時は得失点差→総得点で順位決定）を採用。運用ルールが異なる場合は `ranking.gs` の `calculateTeamRankings` を調整のこと。 |
| **得点者の氏名解決** | `submitScore` は得点者を氏名で受け取り、当該チームの既存ユーザーと氏名一致で解決、未登録なら新規ユーザーとして自動登録する（フロントの入力を簡略化するため）。 |
| **ランキング／アーカイブの自動読み込み回数** | データ未取得時の自動フェッチは1回のみに制限し（`rankingsLoaded` / `archive.yearsLoaded` フラグで制御）、それでもデータが空の場合は手動の「再読み込み」ボタンを表示する。無限リロードを防止するための設計。 |
| **アーカイブ専用のランキングAPI追加** | 過去大会アーカイブ（U06）は、開催中の大会向けランキング（`getRankings`）とは別に `getArchiveRankings` を新設した。チーム順位のソート基準を「総勝ち点」ではなく「1試合あたりの平均勝ち点」に変更している（`calculateArchiveTeamRankings`）。年度をまたぐ複数大会（例: 2025年度の3ラウンド）ではチームごとに試合数が異なりうるため、原本の「順位表」と同じ考え方（平均勝ち点方式）に合わせた。開催中の大会（U05 ランキング画面）は従来通り総勝ち点でソートする。 |
| **アーカイブのチーム順位の表示項目** | 順位・チーム名・平均勝点・試合数・勝点（勝/引/敗）・得失点（得/失）を表示し、上位5件などの制限を廃止して全チームを表示するようにした。個人得点ランキングも同様に全件表示する。 |
| **アーカイブから最新（今年度）の大会を除外** | `getArchiveYears` は現在の年（サーバーの現在時刻の年）を常に除外して年度一覧を返す。開催中／今年度の大会はホーム画面・ランキング画面（現行大会向け）で確認する導線とし、アーカイブは「過去の年度」のみを対象とする。 |
| **運用フローに合わせた5段階ワークフローへの再設計** | 実際の運営シナリオ（①管理者がコートを予約→②各部署に参加を募る→③参加チームが揃ったら対戦表を作成→④内容を確認し試合順を調整→⑤参加者数バランスを確認して確定・公開）に合わせ、管理者ダッシュボードを「①大会作成 → ②コート予約 → ③チーム登録 → ④対戦表自動生成 → ⑤確認・確定」の5段階に再構成した。大会作成フォームからはコート入力・チーム一括登録の欄を撤去し、各工程を独立したステップとして明確に分離している（各カードに①〜⑤の番号バッジを表示）。 |
| **コート予約の独立ステップ化** | 「コート予約 → チーム募集」という運用順序に合わせ、コート設定を対戦表生成から切り離し、`saveCourts` という専用APIで先に保存できるようにした（対戦表はまだ生成しない）。保存したコート構成は `Tournaments.courts` にJSON（名称・予約開始・予約終了の配列）として保持され、④対戦表自動生成の画面では読み取り専用のサマリーとして参照される。 |
| **対戦表自動生成アルゴリズムの再設計（総当たり戦の強制をやめ、試合数の均等化を優先）** | 1大会あたり12部署程度が参加する一方、コート・時間の制約から総当たり戦（12チームなら66試合）は現実的に組めないケースが通常であるため、アルゴリズムを「総当たりを前提に不足したらエラーにする」方式から、「限られた枠の中で全チームの試合数をできるだけ均等にし、同一チームが3試合以上連続しないようにする」ラウンドベースの割り当て方式（`schedule.gs` の `generateBalancedSchedule`）に変更した。コートごとのスロットを「ラウンド」（各コートのN番目の枠を束ねたもの）として扱い、各ラウンドで直近2ラウンド連続出場していないチームの中から消化試合数が少ない順に選出し、未対戦の相手を優先してペアリングする。全チームの総当たりが完了した時点で、枠が余っていても打ち切る。Node.js上で12チーム・3コートの典型シナリオ（全チーム試合数5で完全均等、3連戦0件）を含む複数エッジケースを検証済み。 |
| **対戦表の下書き（DRAFT）→確認→確定（CONFIRMED）ワークフロー** | `Tournaments` に `schedule_status`（空欄 / `DRAFT` / `CONFIRMED`）列を追加し、対戦表生成直後は「下書き」として扱う。参加者向けの `getTournament` は `schedule_status` が `CONFIRMED` になるまで試合データを返さないため、内容を確認する前に参加者へ意図せず公開されることを防ぐ。管理者専用の `getAdminTournamentDetail`（要トークン）は下書き状態でも常に全データを返し、⑤の確認画面で使用する。確定は管理者が明示的に行う専用API `confirmSchedule` で行い、この時点で初めて一般画面の対戦表・順位に反映される。 |
| **試合順の入れ替え機能（当日の遅刻対応）** | 「当日になってから急遽遅刻する部署がある」という実運用に対応するため、⑤の確認画面で2試合を選択すると「時間・コート」だけを入れ替えられる専用API `swapMatches` を追加した。対戦カード（どのチーム同士か）はそのまま維持され、開催枠だけが交換される。確定（CONFIRMED）後も入れ替えは引き続き行え、変更は即座に一般画面へ反映される。 |
| **チームごとの試合数バランス確認画面** | ⑤の確認画面に、チームごとの消化試合数を一覧表示するセクションを設けた。「対戦表が仮で完成したら、各チームの試合数を確認し、同じくらいになれば確定させる」という運用ステップに対応するもので、最小値と最大値が一致していれば「均等です」、差がある場合はその範囲を表示し、確定前に管理者が目視で妥当性を判断できるようにしている。 |
| **チーム登録は1件ずつ追加する方式に統一** | 部署からのエントリーは順次届くのが実態であるため、大会作成時に複数チームをまとめて入力する方式は廃止し、③チーム登録のステップで1件ずつ追加していく方式（既存の `createTeam` API）に統一した。 |
| **管理者ダッシュボードの「登録済み大会一覧」** | `getAdminTournaments` で、全大会をチーム数・試合数付きで一覧表示する。管理者はここから操作対象の大会を明示的に選択でき（`admin.selectedTournamentId`）、②〜⑤の各ステップは常にこの選択中の大会に対して行われる。 |
| **コート予約時間のビジュアルタイムライン（2種類）** | ②コート予約の画面では、試合時間が未確定の段階でも予約状況を把握できるよう、予約時間の帯のみを表示するシンプルなタイムラインを表示する。④対戦表自動生成の画面では、②で保存済みのコートに対して試合時間・第1試合開始時間を加味した詳細なタイムライン（使える範囲・使用不可コートの明示）を表示する。共通の描画ロジック（`renderCourtTimeline`）を両者で共用している。 |
| **背景写真・トロフィー画像の採用** | 画面背景をCSSグラデーションのみから、提供された芝生コート写真に変更。画面幅700px未満はスマホ縦向き写真（`futsal-court-sp.jpg`）、700px以上はPC横向き写真（`futsal-court-pc.jpg`）を`@media`で出し分け、可読性確保のためダークグリーンのグラデーションティントを写真の上に重ねている。背景は`body`要素にではなく`body::before`の`position: fixed`専用レイヤーに持たせており、ページが縦に長くなっても常にビューポート基準で`cover`されるため、スクロールしても写真が引き伸ばされたり見切れたりしない。トロフィー写真（`trophy.jpg`）はホーム画面・ランキング画面冒頭の「ヒーローバナー」として使用。いずれもモバイル回線での表示速度を考慮し、アップロードされたPNGをJPEG（品質80、長辺1000〜1400px）に変換してファイルサイズを約85%削減している。 |
| **大会の削除機能** | 大会一覧の各カードに削除ボタンを追加し、`deleteTournament` API（管理者専用）で大会そのものと、紐づく Teams / Users / Matches / Match_Events をすべて連動して削除する（カスケード削除）。取り消せない操作のため、実行前に `window.confirm()` で確認を必須にしている。汎用ヘルパー `deleteRowsWhere`（`spreadsheet.gs`）を新設し、条件に一致する行をまとめて削除できるようにした。 |
| **「①大会作成」フォームの折りたたみ** | 大会を選択中でも常に「①大会作成」フォームが表示されていると、「また大会を作らないといけないのか」と誤解を招くため、大会が1件も無いとき以外はボタン1つに畳んでおき、必要なときだけ展開する方式に変更した（`admin.showCreateForm`）。作成完了後は自動的に畳まれ、選択中の大会の②〜⑤の手順に視線が戻るようにしている。 |
| **最終試合終了時間（任意入力の上限）** | コートの予約終了時刻とは別に、「最も遅い試合終了時間」を任意で指定できるようにした（初期値 20:45）。試合時間・インターバル・第1試合開始時間をもとにスロットを生成する際、各コートの実終了時刻を `min(コート予約終了時刻, 最終試合終了時間)` としてこの上限でクランプする（`schedule.gs` の `buildCourtSlots`）。コートは21時まで押さえているが「普段は20:45で終える」といった運用差分を、コート予約自体は変更せずに反映できる。未入力なら従来どおり各コートの予約終了時刻のみが上限になる。タイムライン上には黄色（第1試合開始）と赤色（最終試合終了）の縦線で区別して表示する。 |
| **入力順を迷わせないUIの補強** | ④対戦表自動生成のフォーム項目に「①試合時間→②インターバル→③第1試合開始時間→④最終試合終了時間」のインライン番号を付け、上から順に入力すればよいことを明示した。また②③⑤の見出しには、そのステップが完了しているか（②コート予約済み／③チーム2件以上登録／⑤確定済み）に応じてチェックマークバッジを表示し、全体の進み具合を一目で把握できるようにした（`stepBadgeHtml`）。 |

## 主要な作り込みポイント（UI/UX）

- **グラスモーフィズム**: `.glass-card` にすりガラス調の半透明背景＋`backdrop-filter: blur()`。
- **3Dティルト**: `pointermove` で card / scoreboard に `rotateX/rotateY` を適用（`enableTilt()`）。
- **スコアのフリップアニメーション**: `submitScore` 成功時に `.digit-flip` へ `flip` クラスを付与し、CSSの `flipNum` keyframes で回転表示。
- **タブのスライド切替**: ランキング画面のインジケーターを `transform: translateX()` でスムーズに移動。
- **自チーム選択トグル**: 選択していない側の入力欄に `.opponent-locked`（半透明＋`pointer-events:none`）を付与し、誤操作・上書きを防止。
- **モバイルファースト**: タップ領域はすべて `--tap-min: 44px` 以上を確保し、ボトムタブバーで主要導線を固定。
- **氏名の半角→全角スペース自動変換**: 出場メンバーの氏名入力中、半角スペースをリアルタイムに全角スペースへ変換（カーソル位置は維持）。送信時にも再度矯正をかけて二重に担保している。
- **ローディング中のスクロール禁止**: `showLoadingSpinner(true)` 時に `<html>`/`<body>` へ `no-scroll` クラスを付与し、背面コンテンツのスクロールと誤操作を防止。
- **サッカーボールローダー**: ローディングオーバーレイは、白黒の五角形パネルを模したSVGサッカーボールが回転しながらバウンドし、着地のたびに影が伸縮するアニメーションに変更。
- **イベント委譲の一本化**: クリック/入力イベントは `document` 単位で一括委譲する方式に統一。ヘッダー（戻るボタン等）は画面描画のたびに `innerHTML` で差し替わるため、`screenRoot` 限定の委譲だと反応しない不具合があったが、`document` 委譲により解消した。
- **ランキング／アーカイブの単発リロード**: データが存在しない場合の自動再取得を1回に限定し、以降は明示的な「再読み込み」ボタンで再取得する設計とし、無限ループでの負荷増大を防止。
- **対戦表の試合順入れ替えUI**: ⑤確認画面で試合をタップして2件選択すると「入れ替える」ボタンが現れ、対戦カードを維持したまま時間・コートだけを交換できる。当日の遅刻対応を想定した軽量なUI（ドラッグ＆ドロップではなく選択→ボタンの2ステップ）。
- **コート予約のビジュアルタイムライン**: コートごとの予約時間・実際に使える範囲・第1試合開始時間を横棒（ミニガントチャート）で可視化し、数値入力だけでは把握しにくい時間の重なりを直感的に確認できるようにした。
